# Bonsai PTQ1 专项：多优化集成、单 IPA、一次真机自动化性能竞赛

## 一、唯一目标

直接在当前 `MyHerbTea/bonsai-ipad-runtime` 仓库中实施代码修改、原生引擎优化、自动化测试与构建交付。

目标设备：M5 iPad Pro，12GB 统一内存。

唯一模型：官方 Bonsai 2 27B PTQ1_0 GGUF。

**本轮明确排除 PQ2、MLX 迁移、其他模型及无关功能开发。**

最终目标是在同一份 IPA 中集成多个真正实现的 PTQ1 优化候选，由一次真机自动化测试完成候选筛选、参数调优、组合验证、质量检查、稳定性检查和结果打包。

用户不应再为每种优化单独安装 IPA、修改配置或重复运行不同的测试程序。

## 二、先审计真实代码，再直接实现

核查当前仓库 HEAD、未提交修改、PTQ1 TensorOps、Prism 原生补丁、Metal 内核、启动锁存、Governor、KV 管理和 Quick TestKit。

此前报告提到的 `32c479fb...` 等提交只作为检索线索，必须重新核实当前实际状态。

保护现有稳定基线和用户修改，在独立功能分支开发，不直接发布或合并稳定版本。

重点查明：

1. PTQ1 的真实权重解码、Hadamard 变换、矩阵乘与 mat-vec 调用链。
2. TensorOps 是否进入实际推理路径，现有性能门禁是否可能导致候选静默回退。
3. CPU/GPU 同步、command buffer、临时张量和内存搬运的实际实现。
4. batch、ubatch、context、KV 精度在哪个生命周期生效。
5. 如何在同一 App 进程中安全销毁并重建推理上下文，完成候选切换。

审计后直接开始实施。不要重新提交一份研究报告代替代码修改。

## 三、把以下优化候选集成进同一个 IPA

所有候选只使用同一份 PTQ1 模型资产。每个候选使用独立的策略实现、能力检查、诊断记录和回退路径，共享统一的模型管理、测量和结果报告。

### A. SAFE_BASELINE

当前稳定 PTQ1 推理路径，作为性能与正确性基线。

不改变默认生产行为。

### B. PTQ1_TENSOROPS

复用并完善已有的 PTQ1 TensorOps 候选。

重点检查实际 route、pipeline、shape、stride、dispatch、GPU 完成及错误证据。

若现有实现存在门禁不匹配、候选始终回退或计数器只能证明任务入队的问题，应修复真实调用链，而不是只修改诊断显示。

### C. PTQ1_FUSED_KERNEL

实现一个真正的 PTQ1 原生内核优化候选。

优先从真实热点中选择以下方向之一或合理组合：

- 三值权重解码与矩阵乘融合，减少中间权重张量及重复内存访问。
- Hadamard 变换与相邻算子融合，减少重复数据转换。
- 针对 decode 的 mat-vec 路径优化，减少每 token 的调度和数据搬运开销。

必须先确认现有代码的实际瓶颈与兼容条件。不要仅添加一个新类或一个编译开关，就把它命名为优化实现。

### D. PTQ1_LOW_OVERHEAD

根据可获得的源码证据与 profiling，实施独立的调度或同步优化候选。

检查重复资源准备、细碎 command buffer、CPU/GPU 等待、临时缓冲区复制等问题。

只有在确实存在相应开销时才实施。不得为增加候选数量而制造没有依据的实现。

### E. PTQ1_BEST_COMBINATION

对 B、C、D 中独立验证有效的候选，自动构建合理的组合并实际测量。

不允许默认把所有优化强行叠加。组合必须独立验证其正确性、内存和端到端收益。

如果组合产生冲突、重复优化或额外开销，应保留更好的单项方案。

**原则：至少完成已有 TensorOps 的真实验证，并实现有明确代码依据的原生优化。不能把只有设计说明、尚未实现或实际不可达的候选计入有效方案。**

## 四、一次 IPA 内部完成候选切换

实现统一的 `BenchmarkCandidateRegistry` 与 benchmark session 管理器。

在同一个 IPA 中编译并注册全部候选，运行时依次：

1. 验证当前模型、引擎和候选身份。
2. 创建候选所需的执行配置。
3. 预热并执行测试。
4. 收集实际执行与性能数据。
5. 安全停止请求，释放 KV cache、候选专属 Metal 资源及推理上下文。
6. 确认旧运行时已停止，再创建下一个候选。
7. 验证候选确实生效，继续测量。
8. 所有测试完成后恢复安全默认路径。

整个过程只允许一个 PTQ1 模型实例驻留。

不得通过 HTTP 参数假装改变已锁存的后端配置。如果需要重建运行时，应由 App 内部自动完成，不能要求用户反复关闭、重开 API 或重新安装。

如现有架构阻碍同进程切换，直接实现最小必要的生命周期支持，并补充故障恢复测试。

如果某条路线在技术上确实不能安全切换，明确报告具体阻塞原因。不要用不安全的强制切换换取表面上的自动化。

## 五、自动寻找最佳 PTQ1 参数组合

内核候选比较和参数调优分开进行，避免无法判断收益来自哪里。

### 第一部分：内核快速筛选

先统一采用可复现的工作点：

- Context：16K。
- Batch：16。
- UBatch：16。
- KV：Q4_0。
- Flash Attention：开启。
- 序列数：1。

所有候选均读取并记录真实生效配置。

每个候选预热一次，使用相同的约 512 实际输入 token 工作负载测量一次。

先筛除不稳定、无法确认执行、数值检查失败或明显没有收益的候选。

### 第二部分：重点候选对照

对安全通过的基线和最多两个最有希望的候选，使用约 2048 实际输入 token 工作负载进行交错 A/B 对照。

每个正式比较候选至少取得 3 个有效样本，自动处理预热、异常样本和失败重试。

以实际测量选择候选，不按代码复杂度、候选名称或理论峰值排序。

### 第三部分：参数调优

固定胜出的内核实现，自动比较：

- Context：8K、16K、32K。
- Batch/UBatch：优先比较 B8、B16；B24 仅在内存和内核能力检查通过时加入。
- KV：先固定 Q4_0，避免混淆内核收益；只有在安全余量允许且实际使用价值明确时，才追加 Q8_0 对照。

所有参数必须在真实生效的生命周期阶段设置。不得在请求期间伪造动态切换。

采用自适应预算：先完成短输入筛选，再对胜出配置运行 2048 token 和必要的长输入验证。不要让所有配置都跑完整的长时间压力测试。

最终分别给出：

- 日常短中输入的最佳安全配置。
- 长上下文的最佳安全配置。
- 若两者不同，说明取舍并提供自动选择规则。

如果某项配置无法创建、内存不足或出现崩溃，立即记录并安全回退，不再反复触发相同故障。

## 六、统一性能与 GPU 执行证据

每次请求记录：

- 实际候选、源码身份、模型身份。
- Context、Batch、UBatch、KV 精度及后端配置。
- route、pipeline、dispatch、GPU 完成状态与错误。
- 实际输入和输出 token 数。
- Prefill 耗时与 tokens/s。
- 首个 SSE 事件、首个可见内容及最终答案开始时间。
- Decode tokens/s、完整请求耗时、finish reason。
- 进程峰值内存、可用的 Metal 资源数据与热状态。
- 失败、回退、恢复与超时信息。

如果现有计数器只记录 dispatch 入队，增加最小必要的 GPU command buffer 完成/错误诊断。

严格区分候选已配置、路由已命中、GPU 工作已提交、GPU 工作已完成、完整推理成功以及实际性能改善。

不得将 CI 成功、静态链接成功或 GPU 工作入队单独视为性能优化成功。

保留现有数值正确性检查，不得放宽断言或修改阈值制造 PASS。

如果发生失败，应自动保留诊断、保存必要的测试进度并安全恢复；无法恢复时明确报告，而不是静默跳过。

## 九、自动选择最终最佳配置

以安全默认路径为起点，自动选择同时满足以下条件的最佳 PTQ1 配置：

- Prefill 吞吐相对基线提升至少 15%。
- TTFT 改善至少 10%。
- Decode 吞吐回退不超过 5%。
- 新增峰值内存原则上不超过 1 GiB，且始终满足设备实际安全余量。
- 完整答案率不降低。
- 无已确认的关键数值、协议或任务质量回归。
- 通过规定的稳定性检查。

这些门槛是验收要求，不是预先承诺的收益。

如果没有候选达到全部门槛，保留安全基线，输出 `NO_GAIN`，并指出哪些候选因性能不足、执行证据不全或稳定性问题未被采纳。

不得为了选出赢家而降低门槛。
